# decisions.md — 技术决策记录（为什么这样做）

> 上位：spec 的「决策记录」D1–D9（产品级）。本文记录实现级决策及其理由、被放弃的方案。新决策追加在末尾，带日期；里程碑结束时同步回写 spec。

## D5-im 两段式：模型识别、代码算数（2026-09-22）

- **决策**：VLM 只输出菜名/category/分量/置信度，schema 里根本没有营养字段；数值一律 `库中每百克值 × 克数`，代码计算。
- **为什么**：Nutrition5K 等独立评测显示 VLM 直接估营养误差最好也有 ~24%、多数 >40%，是结构性误差源，靠 prompt 压不住。把「这是什么菜」（模型强项）与「到底多少卡」（数据质量问题）拆开后：数值可审计、跨会话一致（不漂移）、模型只影响识别质量，数值质量完全由数据资产决定。
- **配套约束**：库查不到显示「—」待校准，禁止降级为模型估算——一旦允许降级，数值来源就不可信了。

## D7-im 菜品不存营养值，存配方（派生轨）（2026-09-22）

- **决策**：`dishes.json` 存「原料×克数」；运行时 `derivePer100g` 现算（水计入总重保证稀释正确）。
- **为什么**：《中国食物成分表》按**原料**组织，菜品必须靠配方映射；USDA SR Legacy 是公有领域、可按 fdc_id 溯源，原料值实拉而非手写。配方派生让用户差异化成为可能：「放了两克油两个蛋」→ 改配方 → 数值自动重算，这是记卡路里 App 做不到的。
- **已知代价**：配方克数是家庭做法草案，与直录值偏差 >25% 的菜要人工复核（见 known-issues）。

## D8-im 菜肴级双轨制：直录为主、派生兜底（2026-09-24）

- **决策**：常见菜逐菜实拉薄荷食物库值建直录库（每条带 source_url），查找顺序在派生轨之前；派生值与直录值交叉校验（`verify-dishes.mjs`），偏差 >25% 标记复核。
- **为什么**：M1 实测暴露瓶颈是覆盖率而非识别（9/16 待校准）。菜肴级营养全行业都是测算值、不存在政府权威表，薄荷是专业机构测算且国内菜品覆盖最好；诚实原则：来源分级展示（直录参考值/配方派生/类目估算），不冒充精确。

## D9-im 薄荷官方 API 按需补库；批量爬取废弃（2026-09-24）

- **决策**：本地未命中 → 官方 `food/search`（1 次调用即含每百克值+份量单位）→ 结果**永久缓存**进 localStorage；每日软上限 45（官方 50/天）、未命中写永久负缓存。`crawl-boohee-full.mjs` 枚举爬取废弃。
- **为什么废弃爬虫**：枚举爬取触发 429 限流；薄荷网页版已整体下线（首页也 404），只有 App 和 JSON 接口存活。教训：当时仅凭一次 404 就臆断「反爬、浏览器能打开」并继续操作，未交叉验证——此案例已记入根 `MISTAKES.md`，这是本项目的反面教材。
- **为什么按需+永久缓存划算**：自用菜谱高度收敛，查过一次就不再调；「当天额度是白给的，用满不亏」。软上限 45 留 5 次余量防误耗。负缓存防止对确定不存在的菜天天浪费调用。
- **边界**：薄荷免费档不含拍照识别 API，识别仍用 BYOK VLM。

## BYOK + 零服务器（2026-09-22）

- 用户自带 API Key，数据全本地，产品零运营成本（自用月成本 0–15 元）。Key 只存 localStorage，绝不打进 APK。
- 分发（M4）计划走免费轻代理（Cloudflare Worker），让朋友零 Key 使用；三方对比在 M4 决策门（D6），当前不投入。

## 供应商抽象：预设只是默认值模板（2026-09-24）

- **决策**：`providers.ts` 只存 baseUrl/model 建议；baseUrl、model、Key 全部允许用户改写（settings v2）。
- **为什么**：免费额度政策会变，换供应商不应改代码；「custom」预设兜底任意 OpenAI 兼容端点。v1 固定供应商列表已迁移（保留用户已存 Key）。
- **HTTP 细节**：视觉指令并入 user 消息而非 system role（视觉模型对 system 支持度参差）；JSON 解析取首个 `{` 到末个 `}`，zod 全字段 `.catch()` 宽容默认——供应商输出的小偏差不该炸掉整个识别流程；校验失败带错误信息重试 1 次，再失败如实报错。

## 修正引擎：规则层先行，语义层兜底（2026-09-24）

- **决策**：一句话修正先走本地正则（改名/分量/删除/补充/校准五类，即时零成本）；解析不了才调廉价文本模型转成结构化 ops JSON，由**同一套** `applyOps` 本地执行。
- **为什么**：绝大多数修正是「米饭只有半碗」这类硬指令，正则足够；「语义理解交给模型，数值与执行永远留在本地」与两段式同一哲学。规则层解析不了就报「没看懂」并附示例，不猜——猜错用户的饮食记录比不响应更糟。

## 识别缓存 24h，营养数值永不缓存（2026-09-24）

- **为什么**：识别结果只取决于图片+模型，缓存安全省 Token；数值取决于库，而库会因校准/补库/配方覆盖随时更新（`dbTick` 触发重算），缓存数值必然过期失真。

## 网络层：dev 走 Vite 代理，APK 走 CapacitorHttp（2026-09-24）

- **为什么**：智谱/薄荷响应无 CORS 头，浏览器直连发不出去；Vite dev 代理零成本解决开发期问题。原生壳（CapacitorHttp）不受 CORS 限制，届时删除代理依赖（`vite.config.ts` 注释已标注）。代价：静态 web 部署不可用——接受，因为目标形态是 APK。

## 已尝试并放弃的方案

| 方案 | 放弃原因 |
|---|---|
| VLM 直出营养数值 | 误差 ~24%–>40%，结构性（D5，spec 5.2） |
| 批量枚举爬薄荷网页版 | 429 限流 + 网页版下线（D9；误判案例见根 MISTAKES.md） |
| 固定供应商列表（settings v1） | 不满足「换供应商不改代码」，已迁移 v2 |
| 未命中时模型估算顶数 | 破坏数值可信来源，明确禁止（spec 5.2） |

## 特殊约束备忘

- USDA 鸡胸为**熟重**基准、鸡腿为**带皮生重**，配方按各自基准使用（`dishes.json` note）。
- 《中国食物成分表》数据不得原样再分发，自托管自用合规；直录薄荷值仅个人自用不二次分发。
- 薄荷人工核定只能用 JSON 接口（网页版已下线），code 用 `https://food.boohee.com/fb/v1/foods/{code}` 验证（见 `notes/boohee-manual-checklist.md`）。
