# RAG 配料表解读 — 设计思路（大白话版）

> 状态：✅ v1 完成（2026-09-26），本文档记录开发全过程，每一步只写真实发生过的事。
> 位置：`food-nutrition-agent/docs/rag-design.md` · 代码：`app/src/lib/rag.ts`（检索）、`app/src/data/additives-kb.json`（知识库）、`app/src/ai/vlm.ts`（成分提取）、`app/src/ai/chat.ts`（interpret_label 工具）、`app/src/ui/LabelCard.tsx`（卡片）、`app/scripts/rag-eval.mjs`（召回评测）

## 0. 一段话说清楚我们在干什么

拍一张零食背面的配料表 → 模型认出上面写的成分 → 每个成分去**本地知识库**里检索相关资料 → 模型只能**根据检索到的资料**解释每个成分是干嘛的、有没有需要留意的点，并标出来源。资料库里没有的成分，就老实说「暂未收录」，不许现编。

## 1. 为什么配料表适合 RAG，营养数值反而不适合

- 营养数值是**结构化表格**：一个菜名对应一个数，查表 100% 确定，用 RAG 反而可能捞错行——所以主链路用确定性查表（spec D5/D8），这是本项目立身之本。
- 配料表解读是**文字知识**：「卡拉胶是什么」「植脂末为什么被留意」的答案是一段段说明文字，没有唯一数字；而且用户问法模糊（「这个健康吗」）。文字 + 模糊 = RAG 的主场。
- 共同的红线：**不管查表还是 RAG，结论都必须能指回来源**。RAG 版做法：每条知识自带 `source` 字段，卡片逐条标引用编号，模型回答必须引用。

## 2. 设计蓝图（真实数据流）

```
配料表照片 ──► ① VLM 抄文字（vlm.extractLabelIngredients：只提取成分名，不许输出知识）
                │        ▲ 文字路径：用户直接输入「配料表：水、白砂糖、…」跳过这一步
                ▼
           ② 三层检索（lib/rag.ts，全部本地）
              第一层 精确/别名匹配（确定性）
              第二层 语义向量余弦（需 Key，懒构建+永久缓存）
              第三层 关键词字符相似度（零成本兜底，无 Key 时自动降级到这里）
                │
                ▼
           ③ 命中条目 + 未收录清单 ──► interpret_label 工具把资料交回模型
                │                      （模型被提示词约束：只准引用条目与来源编号）
                ▼
           🔎 解读卡片（LabelCard：成分×类别×说明×⚠留意 + 来源清单 + 免责行）
```

## 3. 知识库怎么来的（红线：严禁胡编乱造）

**结构**：45 条，每条 8 个字段——`name`（标准名）、`aliases`（别名，检索用）、`category`（功能类别，如「防腐剂」「甜味剂」）、`fn`（一句话功能）、`safety`（一句话中性安全描述）、`level`（一般/留意）、`common`（常见于）、`source`（引用出处）。

**事实依据怎么保证**：所有「留意」级的结论在写入前**逐组搜索核实**（2026-09-26 实测 4 组搜索），非争议性的功能类别表述引用 GB 2760 的公开分类：

| 核实过的事实 | 写进了哪些条目 | 来源 |
|---|---|---|
| 阿斯巴甜：IARC 2023 归 2B 类「可能对人类致癌」（证据有限）；JECFA 重申 ADI 40mg/kg 体重 | 阿斯巴甜（留意级） | WHO/IARC/JECFA 2023-07 联合评估（中新网/澎湃等报道交叉核对） |
| 反式脂肪酸：WHO 建议每日供能比 <1%（约 2g）；**部分氢化**植物油是主要来源，完全氢化几乎不产生 | 氢化植物油、植脂末、代可可脂（均留意级） | WHO 建议 + 国家食品安全风险评估中心评估（大城市居民供能比 0.34%） |
| GB 2760-2024（2024-03 发布、2025-02-08 实施）：脱氢乙酸及其钠盐在黄油/面包/糕点/淀粉制品等中被删除，仅保留腌渍蔬菜等 5 类 | 脱氢乙酸钠（留意级） | GB 2760-2024 及地方政府官方解读 |
| 亚硝酸钠：腌腊肉制品最大使用量 0.15g/kg、残留量 ≤30mg/kg（2024 版统一收紧）；约 1~3g 可致急性中毒；限量内合规使用评估为安全 | 亚硝酸钠（留意级） | GB 2760-2024 限量 + 公共卫生毒理学资料 |

其余条目（如柠檬酸=酸度调节剂、黄原胶=增稠剂）写的是 GB 2760 功能类别层面的公开事实，`source` 统一标注；软性共识类（如糖醇过量轻泻）标注「公开科普共识」并写明程度。**知识库内容在运行时不参与编造**——它就是检索语料本身，谁写的、写了什么、依据是什么，全部在 JSON 里可审计。

**当前「留意」级共 8 条**：果葡糖浆（游离糖）、脱氢乙酸钠（2025 起多类禁用）、亚硝酸钠（限量与急性毒性）、磷酸盐（总磷摄入）、氢化植物油/植脂末/代可可脂（反式脂肪酸）、阿斯巴甜（PKU 禁用 + IARC 2B）。

## 4. 检索怎么设计（召回准确性）

**为什么是三层**：配料表上的成分名是标准写法，所以第一层「精确/别名」是主力（确定性，不犯错）；用户嘴上和照片里会出现变体（「单甘酯」「AK糖」「含苯丙氨酸的甜味剂」），第二层「语义向量」抓换说法；第三层「关键词字符相似度」零成本兜底——没配 Key 或向量服务挂了，功能也不哑（卡片上会标出用的是哪层匹配）。

**两个阈值**（`rag.ts` 常量，可调）：
- 语义层 `SEMANTIC_MIN = 0.72`：余弦相似度 ≥0.72 才算命中，否则落空。**这是初始值，语义层需配真 Key 才能跑，阈值调优列为待办**（诚实记录：本层离线无法评测）。
- 关键词层 `KEYWORD_MIN = 0.5`：字符二元组 Dice 相似度门槛。**从 0.4 提到 0.5 是被评测逼出来的**（见开发日志 #2）。

**评测怎么做的**（`app/scripts/rag-eval.mjs`，一条命令可复跑）：
- 用例构成：45 个标准名 + 全部别名 + 3 个手写难例（括号备注「阿斯巴甜（含苯丙氨酸）」、句子式「无糖可乐里的三氯蔗糖」、混入杂质词）+ 3 个**必须失配**的反例（迷迭香提取物、氟化钠、贻贝多糖胶）= **118 条**。
- 首轮跑出 **116/118**，3 个失败暴露了 3 个真问题（见开发日志），修复后 **118/118 全过**。
- 评测脚本与 `rag.ts` 是同一套规则的两份实现（脚本侧 Node 无法直接 import TS），改动匹配逻辑必须两边同步——已知的维护成本，记录在案。

## 5. 向量是怎么算出来的

大白话：embedding 就是把一句话变成一串数字（一个高维坐标），**意思相近的话坐标也相近**，于是「找相似说法」变成「算两串数字的夹角」（余弦相似度）。

工程取舍：
- **用谁的 embedding**：智谱 `embedding-2` / 百炼 `text-embedding-v3`，与对话**同一个 Key、同一个根地址**（`providers.ts` 的 `EMBED_MODELS`），BYOK 用户零额外注册；
- **知识库向量懒构建**：首次使用解读功能时才把 45 条知识逐条向量化（约十几秒），结果永久存 localStorage（`fna.rag.emb.v1`）；知识库升级（version 字段变化）或换 embedding 模型时自动重建；每 4 条一批串行防限流，每批落盘、中断可续；
- **查询向量运行时现算**：每次解读每个成分 1 次调用（毫秒级返回，成本可忽略）；
- **没 Key？** 自动跳过向量层，用关键词层顶上——功能不哑，只是少一层语义匹配。

## 6. 模型怎么被拴住

三个环节层层设防：
1. **提取阶段**：VLM 的提示词只允许「看图抄文字」，输出 `{"ingredients": [...]}`——它是感知工具，不是知识来源；
2. **检索阶段**：完全本地，模型根本不参与；
3. **解读阶段**：工具返回给模型的指令明确要求——只能引用条目内的信息与来源编号；未收录成分不要猜测其作用；结尾提醒「仅供参考、不构成医疗建议」。卡片本身也自带来源清单和免责行，即使模型跑偏，卡片上的事实仍是知识库原文。

mock 模式（无 Key）下输入「配料表：水、白砂糖、…」即可走通「解析→检索→卡片」全链路（向量层自动降级），这也是 E2E 的测试通道。

## 7. 开发日志（问题与修复，真实记录）

1. **构建门禁**：`executeTool` 解读分支里写了不存在的 `i.hit` 属性（`LabelHit` 的字段是 `entry`/`matchType`），tsc 报 TS2339——修正后通过。
2. **评测首轮 116/118，3 个失败全是有价值的真问题**：
   - 「葡萄糖浆」被果葡糖浆抢走（exact）→ **知识库错误**：葡萄糖浆和高果糖浆是不同产品，我误把前者写成了后者的别名——删别名（KB 是人写的，人就会错，评测就是为此存在的）；
   - 「无糖可乐里的三氯蔗糖」命中了白砂糖 → **子串陷阱**：「三氯蔗糖」里包含「蔗糖」，0.85 子串加权打平后按顺序被白砂糖抢先——改为随名字长度递增的加权（长名 0.84 > 短名 0.82），长名优先；
   - 「迷迭香提取物」误命中酵母抽提物 → **短文本假相似**：两者共享「提取/取物」二元组，Dice 0.44 越过 0.4 阈值——阈值提到 0.5（合法别名都走精确层，不受影响，评测复跑确认）。
3. **E2E 环境**：沿用本会话验证过的页面内原生事件通道（原生 setter+input 事件+element.click），绕开 Playwright fill/Enter 竞态与点击超时——没有新增坑。
4. **修复后**：评测 118/118，E2E 两条用例全过（混合命中+诚实未收录；3 个留意级 ⚠ 均带核实来源；括号变体被关键词层兜住，卡片如实标注「关键词匹配」层级）。
